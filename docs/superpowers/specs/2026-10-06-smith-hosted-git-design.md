# Smith-hosted git: repositories on the workspace's machines, reached only through the coordinator

**Status:** milestones 1 to 3 implemented 2026-10-06 (host, serve, build from the copy; replication and failover; backups to R2 and restore), plus from milestone 4: Pull/Push/Detach for Smith-hosted copies and the v2 advertisement and `ls-refs` answered from the record. Remaining polish: `bundle-uri`, streaming, scheduled re-sync.
**Plan:** [docs/superpowers/plans/2026-10-06-smith-hosted-git.md](../plans/2026-10-06-smith-hosted-git.md).
**Scope:** the Cloudflare-hosted coordinator (`cloudflare/coordinator/`) and the hosted native agent
(`Modules/SmithAgent/Hosted*.cpp`). The LAN coordinator is unchanged.

## Context

Smith's hosted coordinator is a Cloudflare Worker at `https://exp.redmarmosetstudios.com` with one SQLite Durable Object (DO) per workspace, D1 for identity and R2 for agent packages. Native agents connect **outbound only** (a `curl` subprocess per request, claims polled every 3 s, heartbeat every 20 s) and build from GitHub or any Git URL with the machine's own git login.

The dashboard already promises **"Keep a copy in Smith" / "Copy into Smith"**, but that copy is implemented on Cloudflare Artifacts, which **is not available on the account in use** (`docs/cloudflare/progress.md`, 2026-10-06), is Workers-Paid-only, bills from 2026-10-14, caps repos at 1 GB and never syncs after the one-shot copy. The autonomous crew is paused on this account because it needs that copy. So the copy slot exists in the UI and nothing fills it.

The request: make Smith itself the git host.

1. Copy repos onto agent machines and **serve git from them**.
2. **Robust**, with **free backups**: a lost agent is restorable, ideally because other agents hold copies.
3. Find **free storage** suitable for off-machine backups of repos of tens of MB.
4. People reach repos over the web **only through the coordinator** (`https://exp.redmarmosetstudios.com/git/<repo>`); agents are never exposed.
5. Low friction, secure, safe, robust; **no new user settings**. Reuse what Smith already has: node credentials, personal access tokens (PATs), the machine's git login, the Cloudflare account and its R2.

## Research conclusions (what decided the design)

The research was done with web searches against Cloudflare's Workers, R2 and Durable Objects limits pages, git's protocol documentation (`gitprotocol-http`, `gitprotocol-v2`, `git-receive-pack`, `githooks`), the Gitaly Praefect and Gitea mirror designs, and the free tiers of every storage candidate named below.

- **Agents cannot do WebSockets.** Their only HTTPS client is the `curl` CLI (no native TLS, by design). Windows' System32 curl 8.13 advertises `ws` but the CLI has no bidirectional mode; macOS (8.7.1) and Ubuntu 24.04 (8.5) curl lack it. The coordinator-to-agent leg must therefore be plain HTTPS requests the agent initiates. **Cloudflare Tunnel is rejected**: free, but it needs a daemon per agent, a tunnel token per agent and a public hostname per agent, which is exactly the exposure and friction ruled out.
- **Cloudflare limits allow a relay on Workers Paid**, which the account already is on. Request bodies are capped at **100 MB on every request** (zone plan), including requests agents make to the Worker; response bodies are unlimited; a request may run as long as the client stays connected; waiting on I/O costs no CPU; isolates have 128 MB so bodies stream, never buffer. R2 `put()` needs a known length, so unknown-length bodies go up as 5 MiB multipart parts. A DO stays in memory 70 to 140 s after its last request, so the existing 3 s claim polls already keep every workspace DO hot around the clock: new polls add requests, not duration.
- **Free backup storage: Cloudflare R2.** 10 GB-month, 1 M writes, 10 M reads per month, **zero egress**, Standard class, already in the account. Thirty repos at 50 MB with two full generations plus incrementals is 3 to 4 GB. Everything else investigated is worse here: Artifacts (paid, 1 GB/repo, beta), Backblaze B2 (needs a new account and key), GitHub private repos (no provider diversity, needs repo-creation rights), GitLab/Codeberg (new accounts; Codeberg forbids mirrors), Google Drive/OneDrive (OAuth plumbing), Storj (free tier ended 2024), D1/KV/DO storage (2 MB and 25 MiB value caps). `git bundle` is the right format: self-contained, verifiable, incremental, restorable with plain git; bundles do not record HEAD, so the default branch lives in coordinator metadata.
- **Serving git from an agent** is `git upload-pack --stateless-rpc <dir>`, `git receive-pack --stateless-rpc <dir>` and `--http-backend-info-refs <dir>` through the `git` front end (Windows finds `git-core` via the exec path). Direct invocation avoids `git http-backend`'s CGI path concatenation and dumb-HTTP defaults. Git clients gzip POST bodies over 1 KiB; the Worker inflates them. Protocol v2 arrives as a `Git-Protocol: version=2` header that must become `GIT_PROTOCOL`; pushes are v1 only.
- **Replication model** (Gitaly Praefect, Gitea mirrors): the coordinator is the ref-tip source of truth with a per-repo generation counter; exactly one primary accepts writes; replicas fetch with `--prune --atomic` (git ≥ 2.36 for atomic pruning); a replica is "current" only when its tips equal the record; reads go to the primary or a current replica, never a stale one; failover promotes only a current replica. Mirror-refspec pruning deletes any local ref the remote lacks, so quarantine namespaces must be excluded from the refspec and digest.
- **Security brief**: HTTP Basic over HTTPS with a token as the password and a 401 `WWW-Authenticate: Basic` challenge is what git clients and credential helpers (Git Credential Manager, osxkeychain, libsecret) expect; helpers key on host plus username, so the clone URL carries a username per workspace; repo names are allow-listed and mapped to internal IDs; the agent never sees client paths; node credentials are rejected on `/git/*`; the agent serves only what a coordinator-issued ticket names; rate-limit by token and by IP for failures; log who/what/when without secrets; a non-fast-forward cannot be detected before the pack arrives, so branch protection must be git-native (an `update` hook over the quarantine), not a pre-parse.

## Design

### 1. Public endpoint: `https://exp.redmarmosetstudios.com/git/<repo>`

- `<repo>` is the project ID (`[a-z0-9][a-z0-9-]{0,63}`), optional `.git` suffix. Only smart-HTTP paths: `GET info/refs?service=git-upload-pack|git-receive-pack`, `POST git-upload-pack`, `POST git-receive-pack`. Everything else under `/git/` is 404. No dumb HTTP.
- **Authentication**: `Authorization: Basic base64(<username>:<credential>)` or `Bearer`. The credential is either a PAT (`smith_pat_<ws64>_…`) or a **git ticket** (`smith_git_<ws64>_…`, new prefix routed to `git_tickets`, never to `access_tokens`). Both embed the workspace, so the repo is resolved inside it; a repo in another workspace is 404 (no existence oracle). Unauthenticated or expired/revoked → true `401` with `WWW-Authenticate: Basic realm="Smith", charset="UTF-8"` so helpers discard and re-prompt. Cookies never. Node credentials (`smn.…`) rejected by pattern. Run tokens (`smith_run_…`) → 403.
- **Clone URL carries the workspace as the username**: `https://<first 12 hex of workspace id>@exp.redmarmosetstudios.com/git/<repo>.git`. Helpers then store one credential per workspace. When the username is a 12-hex string it **must** equal the credential's workspace prefix, otherwise 401 (so a helper that stored the wrong workspace's token discards it).
- **Credentials people use** (owner's decision: valid until revoked): the Clone dialog mints a **git credential**: a token with scopes `read` (+ `build` when the person's role allows it), **no expiry**, revocable with one click, named after the machine, shown once with the full `git clone` line, with last-used time in the token list. The existing 7/30/90-day PATs also work.
- **Scopes** (owner's decision): `read` → `git-upload-pack`; the existing **`build`** scope → `git-receive-pack`. No new scope: a token that can start builds can push. Enforced at use time by adding `git-read` and `git-clone-info` to the read-only action list in `WorkspaceCoordinator.execute` and leaving `git-write` out, so a member demoted below operator loses push immediately. Crew runs never use their run token for git; they get tickets (§3).
- **Rate limiting**: Workers Rate Limiting binding (`ratelimits` in `wrangler.jsonc`) keyed by credential hash for successes **and by client IP for 401/403 outcomes** (a brake, per-colo and approximate); the authoritative limits are per-workspace quotas in the DO (`git-authorize`: RPCs per minute, inflated bytes per day). The request body is cancelled on any pre-relay failure; the relay opens only after authorization succeeds.
- **Errors readable by git**, with exact texts in the tests: `info/refs` failures are pkt-line `ERR <message>` (git prints `fatal: remote error: <message>`): "No machine holding this repository is online. <primary> is offline; start it to restore service", "This Smith token cannot push. In the dashboard, create a token with 'Push to Smith's copies' and use it as the password", "This token belongs to another workspace", "This repository is restored from a backup and refuses pushes until an owner accepts the restore". POST failures: plain text with 401/403/404/413 ("push larger than 100 MB")/429/504 ("push outcome unknown; run git fetch and push again"). Responses carry `Cache-Control: no-cache, max-age=0, must-revalidate`.
- Route position: in `index.ts` `route()` right after `handleAuth` and before the `/downloads` match, ahead of the ASSETS fall-through, the `/api/v2` Origin check, the GET/POST gate and the JSON `readBody`.

### 2. The relay: how a request reaches an agent that only polls

Agents poll; the coordinator never dials in. Each git RPC is one rendezvous through an **R2 mailbox**:

1. The Worker authenticates, applies rate limits, and asks the workspace DO (`git-relay-open`) for a relay: repo, service, writer flag, target node (primary for writes; primary or a current replica for reads), `relayId`, lease token, lease length (120 s read, 120 s write by default, extendable by renew). No eligible node online → immediate `ERR`.
2. The Worker inflates `Content-Encoding: gzip` with `DecompressionStream` (malformed gzip → 400) while **capping inflated bytes**: 16 MiB for `git-upload-pack` bodies (negotiation only) and 100 MiB for `git-receive-pack`; over the cap it aborts the multipart upload and answers 413. It buffers up to 5 MiB; a body that ends sooner is one `put`, otherwise 5 MiB multipart parts, to `relay/<ws>/<relayId>/req`. Then it marks the relay `ready`.
3. The host agent's **git thread** polls `POST …/git/poll` (node credential) only while the node hosts at least one repo or has a pending task; every 3 s idle, every 500 ms for 60 s after activity ("hot mode"). The DO hands it the oldest `ready` relay addressed to that node. **Each poll renews every relay and task the node holds.** A writer relay is **never re-leased**: if its lease expires the relay fails with the 504 text above and the DO queues a tips re-read from the primary so whatever landed is adopted. A reader relay may be re-leased to another node, and each execution writes under its own key (`res-<leaseToken>`) so two executions never interleave.
4. The agent calls `git-relay-body-start` (the DO verifies the relay is leased to this node and unexpired and returns the R2 key), downloads the body through the Worker, runs the git service on its bare repo with stdin from the file and stdout to a private file, then uploads the output **in 5 MiB chunks, one request per chunk** (`POST …/git/relay/:id/response?part=N`, each an R2 `uploadPart`), finishing with a completion that carries the lease token, exit status, total byte count, SHA-256 and, after a receive-pack, the new tips. The Worker completes the multipart upload, checks the byte count against the declared total, and only then calls `git-relay-complete` (idempotent; 409 if the lease token is stale; a **late completion of an expired writer relay still records its tips**).
5. The Worker, which blocked on `git-relay-status` (the DO holds the RPC up to 25 s and re-issues; no 1 s polling), streams the R2 response object to the client with the right `Content-Type`, marks the relay `delivered`, and deletes the objects. Lifecycle rules are the fallback for undelivered objects.
6. Bucket lifecycle: delete `relay/` objects after one day and abort incomplete multipart uploads after one day; the DO also aborts the request upload when the client stream errors.

The DO records new tips **before** the client sees the push report. A push whose completion is lost still lands (the agent journals every relayed receive-pack locally and reports pending completions on its next poll; the DO adopts them).

Why a mailbox and not a stream through the DO: it is simpler, restartable and memory-safe, and the chunked uploads sidestep the 100 MB request cap for clone responses and backups. Streaming through a `TransformStream` is the later optimisation if latency matters.

Latency: 2 to 4 s per RPC cold, 1 to 2 s hot. A protocol-v2 clone is three RPCs, so a 30 MB repo clones in well under half a minute; the first RPC pays the idle poll.

### 3. On the agent: the `smith-git-host` capability

- **Eligibility** is both machine and workspace: the agent advertises `smith-git-host` when git ≥ 2.36 (`git --version` via `HostedToolVersion`; atomic pruning needs 2.36; Ubuntu 22.04's 2.34 is documented as needing the git PPA), `git --exec-path` exists, the store root could be created owner-only, and free disk is above 2 GB; re-evaluated at each heartbeat, and the heartbeat carries a `hosting: {able, reason, free}` object (with the existing 400 strip-and-retry fallback) so the machine card can say "not hosting: git 2.28 is older than 2.36" or "only 1.2 GB free". **Hosting is opt-in per machine** (owner's decision): nothing hosts until an owner or admin flips **"Keep copies of repositories here"** on the machine card (a `host_repos` flag on `nodes`, set through a `node-host` action exactly like the existing `run_crew` / `node-crew` toggle; schema version 11). The DO then hosts only on nodes that are labelled, `purpose = 'build'`, and switched on in that workspace; the switch is per workspace, so a machine linked into several workspaces hosts only where it was switched on. Personal machines cannot be switched on. Losing the label (disk full) counts as the primary being unavailable (§5); switching a primary off runs promotion first and then a `discard` task.
- **Store**: `<hosted-workspace>/git/<ws12>/<repoUuid>.git`, keyed by a repo UUID (not the project ID, so a deleted-and-recreated project cannot collide), created with `HostedSecureDirectory`, outside the `jobs/` root; paths validated with the existing `Contained` helper (moved out of its anonymous namespace). Per-repo config at creation: `receive.fsckObjects=true`, `transfer.fsckObjects=true`, `fetch.fsckObjects=true`, `receive.maxInputSize=100m`, `receive.advertiseAtomic=true`, `uploadpack.allowFilter=true`, `core.hooksPath=<agent-owned hooks dir>`. The agent **snapshots the bare repo's config** at creation and refuses to serve, replicate or report tips for a repo whose config changed (the `SnapshotGitConfig`/`GitConfigTrusted` pattern from `HostedAiSession.cpp`).
- **Ref policy is git-native.** The agent provisions one `update` hook (`#!/bin/sh`, which Git for Windows runs through its bundled sh) in an owner-only hooks directory. Per relay it passes `SMITH_PROTECTED_REFS`, `SMITH_ALLOWED_REFS` and `SMITH_DENY_DELETE` in the environment; the hook refuses refs outside the allow patterns, deletions where denied, and non-fast-forward updates of protected refs using `git merge-base --is-ancestor` over the quarantine objects. Default policy for a human `push` credential: `refs/heads/*` and `refs/tags/*` allowed, the default branch protected from force-push and deletion, other branches free. The agent's pkt-line pre-parse is kept only to reject unparseable command lists early (deny-by-default on `shallow`, `push-cert`, push options) with the refusal framed per the client's advertised capabilities.
- **Git thread** (`RunHostedGitLoop`, modelled on `RunHostedAiLoop`): independent of the build loop so hosting continues during builds. Polls, serves relays, reports tips, runs replicate/backup/restore tasks when idle, disables itself on 404 from an older coordinator. **Self-update waits for no relay in flight**, exactly as it waits on `aiBusy`.
- **Serving env**: `GIT_PROTOCOL` from the ticket, `GIT_CONFIG_NOSYSTEM=1`, an empty `GIT_CONFIG_GLOBAL`, `GIT_TERMINAL_PROMPT=0`, `GIT_*` and credential/deploy variables unset (`ProcessOptions::envUnset`), `stopWithParent`, timeout from the ticket. Before a receive-pack the agent checks free disk ≥ 3 × declared body length + 1 GiB, and after it runs `git count-objects -v`; a repo over the 1 GiB cap is reported `oversize` so replication does not fan out.
- **Replicate, restore and backup children** also run with `GIT_CONFIG_NOSYSTEM=1`, empty global config and `credential.helper=` (empty), so an expired ticket can never fall through to, or erase, the human's stored PAT. Only the `host` job's clone of the external source uses the machine's own git login.
- **Tips**: after every receive-pack, fetch and bootstrap, `git for-each-ref` over everything except `refs/smith/*`, posted as a JSON list (own 1 MiB cap on `git/tips`) with a SHA-256 digest; the digest also rides on `git/poll`. A repo with more than 10,000 refs is refused at hosting time with a clear message. The agent also keeps a local **relay journal** (relayId, post-receive tips) so completions lost in transit are reported on the next poll.
- **Builds on the hosting machine** use a `file://` clone of the local store **only when the DO marks the node current or primary for the repo's generation at claim time** and passes the expected tip; the agent verifies the tip (and, for pinned builds, that the commit exists) before building, uses `--no-hardlinks`, and otherwise falls back to the relay with a ticket.
- **Transport**: the curl `Transport` moves to `HostedTransport.{h,cpp}` and gains `Transfer(route, method, bodyFile, outFile, headersFile, timeout, maxBytes)` with chunked part uploads. `ProcessOptions` gains `stdoutFile` (in `Process_Windows.cpp` and `Process_Posix.cpp`) so packfiles never pass through the line-splitting reader. **Job directory cleanup** (`jobs/<uuid>` removed after `Complete()`, keep the last few) lands in milestone 1 because hosting makes disk pressure matter.
- **Redaction**: tickets join the secrets list; the git thread uses the overlap-safe `HostedRedact` (redact before truncation).

### 4. Coordinator state (new module `cloudflare/coordinator/src/git-host.ts`)

A `HostedGit` helper class over the workspace DO's `sql` (the `RepoAccess`/`Setups` pattern; `workspace.ts` is far past the 800-line limit and only gains dispatch lines). New tables need no schema-version bump.

- `git_repos(id PK, project_id, uuid, default_branch, primary_node_id, generation, state hosting|bootstrapping|degraded|lost|oversize|deleted, source_url, refs_json, refs_digest, bytes, last_push_at, last_backup_at, created_at, degraded_reason)` — tips stored as one JSON blob plus digest (one write per push; the 2 MB row cap is far above 10,000 refs).
- `git_recovered(repo_id, node_id, ref, sha, recorded_at)` — quarantined refs a node kept that the record never had.
- `git_replicas(repo_id, node_id, state bootstrapping|current|stale|diverged|lost, generation, tips_digest, bytes, last_sync_at, next_attempt_at, PK(repo_id,node_id))`
- `git_relays(id, repo_id, node_id, service, writer, state open|ready|leased|completed|delivered|failed, lease_token, lease_expires_at, req_key, res_key, status, size, sha256, created_at)`
- `git_tasks(id, repo_id, node_id, kind replicate|backup|restore|discard, state, lease_token, lease_expires_at, attempts, next_attempt_at, payload)` — recurring work, deliberately **not** in `jobs` (the `busy_node` unique index would block builds and the 1,000-lifetime-job quota would be exhausted).
- `git_tickets(hash, repo_id, scope read|write, node_id NULL, job_id NULL, attempt_id NULL, ref_policy, expires_at, revoked_at)` — hashed, minted inside the transaction. **Node-bound tickets** (replication, builds, AI turns) are presented together with the node credential (git sends both as extra headers via `GIT_CONFIG_COUNT=2`); the Worker accepts them only when the node header matches. Build tickets are bound to the job attempt and revoked at complete/cancel/lost; TTL = job timeout + 10 min, minted at **claim** time, never stored in `jobs.specs`. Node revoke revokes the node's tickets.
- `git_backups(id, repo_id, kind full|incremental, key, size, sha256, tips_json, base_id, ready, created_at)` — two-phase like artifacts: reserve → upload → `ready=1`.
- `git_audit(at, workspace, token_prefix, repo_id, service, node_id, bytes, result)` (CR/LF stripped, no secrets), pruned to 30 days.

Actions through `execute(principal, action, body)`: `git-authorize`, `git-relay-open/-status/-body-start/-response-start/-complete`, `git-poll` (renews; answers for every eligible linked workspace in one round), `git-tips`, `git-task-start/-complete`, `git-backup-start`, `git-clone-info` and `git-credential-create` (human, read), `host-project` (owner/admin), `git-accept-dataloss` (owner/admin), `git-discard-recovered`/`git-promote-recovered` (owner/admin). Human routes in `index.ts`: `POST projects/:id/host`, `GET projects/:id/clone-info`, `POST projects/:id/git-credential`, `POST projects/:id/accept-dataloss`, `POST projects/:id/recovered/:action`. The alarm gains `reconcileGit()`: expire relay/task leases (tasks requeue only when the node is offline past the threshold), fail expired writer relays and queue tips re-reads, abort orphaned multipart uploads, debounce backups, settle `host` jobs that ended failed/lost/cancelled (the `reconcileMirrors` pattern), run promotion when the primary is unavailable, prune audit rows.

### 5. Hosting, replication, failover, divergence

- **Hosting a project** (`host-project`, reached from "Copy into Smith" / "Keep a copy in Smith"): creates the `git_repos` row (`bootstrapping`) and queues a **`host` job** (a real job like `mirror`, visible in Builds as "copy into Smith", cancellable) with required label `smith-git-host` and the `repo_access` requeue predicate extended to it. **Whichever eligible node completes the job becomes primary** (not pre-chosen). The agent clones `--mirror` into `<uuid>.git.tmp-<jobId>` with its own git login (the mirror job's 1 GiB size check), applies config and hooks, records `git symbolic-ref HEAD` as the default branch (fallback: the project branch; hosting is refused if both are unknown), renames into place, reports tips. On completion the DO sets generation 1, switches `project.repoUrl` to `https://exp.redmarmosetstudios.com/git/<id>.git` (keeping `sourceRepoUrl`), and queues `replicate` tasks for every other eligible online host (no debounce for the first one) plus a `backup` task. Failed/lost/cancelled host jobs settle to `failed` with the reason on the card and leave `repoUrl` untouched.
- **Writes** are relayed only to the primary. A completed receive-pack bumps the generation, replaces `refs_json`, marks other replicas `stale`, queues `replicate` tasks and a `backup` task (5 min debounce).
- **Replicate task**: `git fetch --prune --atomic <relay URL> '+refs/heads/*:refs/heads/*' '+refs/tags/*:refs/tags/*' '^refs/smith/*'` with a node-bound read ticket through `GIT_CONFIG_*` (`HostedGitAuthEnv`), the allow-list extended from `*.artifacts.cloudflare.net` to `<the agent's own coordinator origin>/git/<name>.git` and the header key path-scoped with a trailing slash (`http.<origin>/git/<name>.git/.extraheader`; git treats a configured URL as a prefix only when it ends in `/`). The replica reports tips; it becomes `current` only when its digest equals the record. Every eligible host ends up holding every repo in the workspace (max 5 replicas per repo; placement by free disk, requiring free disk > 2 × repo bytes + 1 GB).
- **Reads** go to the primary when online and labelled; otherwise to a `current` replica; otherwise `ERR` naming the offline primary. Never stale data.
- **Primary tips are authoritative** while a node is the recorded primary and no promotion has happened: a digest change on the poll triggers a full tips read and the record adopts it (generation bump, replicas stale, replicate and backup queued). If the change is not explained by a journaled relayed receive-pack, the repo is additionally flagged on the card ("<host> changed the repository outside a push") and backups pause until an owner acknowledges, because a build on that machine could have written into the store (see §8 trust boundary).
- **Failover**: when the primary is unavailable (offline past `nodeOfflineSeconds`, revoked, drained, or label lost) and a write arrives or the alarm runs, the DO promotes a `current` replica whose generation equals the repo's. None → writes refused (`lost` for writes), reads from whatever is current, and the card says which machine to start. Split brain is structurally impossible: agents accept pushes only as relays addressed to them and the DO addresses writes to exactly one node.
- **Divergence** is general: any node (former primary or replica) whose reported tips contain refs or SHAs the record lacks is `diverged`. The agent moves those refs to `refs/smith/recovered/<timestamp>/*` (excluded from the digest and from pruning), reports them to `git_recovered`, then re-syncs. The card lists them with **Promote** (fast-forward the record to include them, when they descend from the recorded tips) and **Discard**. Nothing is deleted silently.
- **Revoke/drain** of a primary runs promotion at once. **Project delete** marks the repo `deleted`, queues `discard` tasks (store moved to a trash folder, purged after 7 days), keeps backups 30 days; hosting a project ID that still has a non-deleted row is refused.

### 6. Backups to R2, restore and data-loss acceptance

- New bucket `smith-experiment-git` bound as `GIT` (operator creates it once with the two lifecycle rules; `DeployWorker.bat` fails early if the binding's bucket is missing). Prefixes `relay/` and `backups/<ws>/<repoUuid>/`. R2 server-side encryption is the only protection for relay bodies at rest, which is stated in the docs.
- **Backup task** (on the primary, idle only): weekly `git bundle create --all` (full) and, after pushes, `git bundle create <file> <new tips> ^<tips of the newest ready bundle>` (incremental); on "bad revision" (a force-pushed base was gc'd) or a chain older than four weeks, a full. `git bundle verify`, then **reserve a `git_backups` row → upload in 5 MiB chunks through the Worker with SHA-256 and byte count verified → `ready=1`**. The manifest records tips and default branch. Retention: keep the two newest fulls and the incrementals since the older one; delete the rest. Budget: 8 GB of the account's 10 GB free tier for backups (the releases bucket and transient relay data take the rest); when a new full would exceed it the DO deletes the older full first (one full is better than none). The card shows "last successful backup at …" and warns when older than 7 days or when the repo is `oversize`.
- **Recovery order** when a repo has no online current replica: (1) an online replica whose tips equal the record → promote; (2) the online replica with the highest generation whose refs are a subset of the record → promote and mark `degraded` only by the delta; (3) a `restore` task on an eligible node: download the newest full and following incrementals through the Worker, `git clone --mirror <full.bundle>` into a temporary directory, `git fetch <inc.bundle> '+refs/*:refs/*'` in order with `git bundle verify` each, delete refs absent from the newest manifest (bundles cannot express deletions), set `HEAD` from the recorded default branch (else project branch, else first head, and say so), `git fsck --connectivity-only`, swap into place atomically (never over an existing store; a node already holding the repo is not a restore target), report tips. Then fetch from any stale replica that holds newer refs before computing the delta.
- Restored tips equal the record → primary, done. Record newer than the restore → **`degraded`**: reads served, writes refused with the `ERR` text, and the card shows "Restored from the backup of <time>; <N> refs are newer in Smith's record and may be lost", listing every known copy (online or not) and which ones hold newer refs. **Accept** (owner/admin) replaces the record with the restored tips and is refused while any online copy holds newer refs unless that copy is explicitly chosen to discard; until Accept, replicas with newer refs quarantine them into `refs/smith/recovered/*` rather than pruning.
- Honest claim: a lost machine costs at most the pushes of the last few seconds that no replica had fetched yet, and off-machine copies lag by up to five minutes; the card shows per repo how many machines hold the current generation.

### 7. Dashboard

### 8. Security and trust boundary

1. Basic/Bearer only on `/git/*`; cookies, node credentials and run tokens rejected; true 401 challenge; 404 cross-workspace; 403 scope; username cross-checked.
2. Repo name allow-list → internal ID; the agent receives `{repoUuid, service, writer, refPolicy}`, never a client path.
3. Direct `upload-pack`/`receive-pack`; no http-backend, no dumb HTTP; agent-provisioned `update` hook; fsck on receive, transfer and fetch; `receive.maxInputSize` plus disk pre-check and post-push size check; no shared object stores; timeout and `stopWithParent` on every git child; config snapshot verified before every serve.
4. Tickets hashed at rest, short-lived, repo-scoped, node-bound where a node presents them, bound to the job attempt for builds, delivered only via `GIT_CONFIG_*` env with the user's git config disabled, redacted before truncation.
5. Blob routes (`relay body`, `relay response`, `backup`) are authorised by a DO `*-start` action that checks the lease belongs to the calling node; the Worker uses only the key the DO returns; completion requires the object to exist with the declared size and hash.
6. Gzip and disk bombs: inflated-byte caps per service, multipart abort, workspace byte quotas, replication stops for `oversize` repos.
7. Rate limits per credential and per IP for failures; DO quotas authoritative.
8. Audit table without secrets; CR/LF stripped.
9. **Trust boundary, stated plainly**: a hosting machine's bare stores live under the same OS user that runs that machine's builds, chats and crew runs. Hosting is therefore only as trustworthy as the code the machine builds, which is why hosting is a deliberate per-machine switch an owner/admin flips, stores sit outside the build roots, config is snapshot-verified, unexplained tip changes pause backups and are shown, and the blast radius of a compromised host is its owner's hosted workspaces. The docs say: do not host on a machine that builds untrusted projects.
10. No real deploy, publish or external push during development (CLAUDE.md). Tests use local bare repos and fakes.

### 9. Decisions made (with the owner, 2026-10-06)

1. **Push uses the existing `build` scope** (owner's choice, 2026-10-06); no new scope. A member demoted below operator loses push immediately.
2. **Git credentials are valid until revoked** (owner's choice), minted from the Clone dialog with last-used shown; the 7/30/90-day PATs still work.
3. **Agent hosting replaces Artifacts as "Smith's copy"**; Artifacts stays as an optional path, offered only when hosting is unavailable and Artifacts is available.
4. **Hosting is a per-machine switch** (owner's choice): only build machines an owner/admin switched on in that workspace hold copies; personal machines cannot be switched on. Every switched-on host replicates every repo (max 5).
5. **Default branch protected** from force-push and deletion for human credentials via an agent-provisioned `update` hook; other branches free.
6. **All R2 traffic goes through the Worker** in 5 MiB chunks (no S3 keys), which lifts the 100 MB cap off clone responses and backups; inbound pushes stay capped at 100 MB per push.
7. **Relay bytes use an R2 mailbox**; writer relays are never re-executed; reads may be.
8. **Store paths and backup prefixes are keyed by a repo UUID**, not the project ID.
9. **AI chats and crew runs get tickets in milestone 1**, because `repoUrl` switches in milestone 1.
10. **Crew push policy is `refs/heads/smith/crew-<slug>-*`**, matching the existing branch convention in `crew.ts` and `HostedAiSession.cpp`.


### 10. What milestone 1 actually built (deviations from the sections above)

- Node-facing routes are `POST /git/poll` and `POST /git/tips` plus the three raw relay routes
  `GET /git/relay/:id/body`, `POST /git/relay/:id/response?part=N` and `POST /git/relay/:id/complete`
  (lease token in `X-Smith-Lease-Token`). The `git-relay-*-start` authorisations of §4 became the
  Durable Object actions `git-relay-body`, `git-relay-response`, `git-relay-upload`, `git-relay-part`,
  `git-relay-finish` and `git-relay-complete`, called by the Worker for the machine.
- Heartbeats answer `gitHost: true|false` (the machine is switched on and able in some linked workspace);
  the agent's git thread polls only while that is true.
- Git credentials are ordinary personal access tokens created with `expiresInDays: null`
  (`neverExpires` in the token list); there is no separate `git-credential-create` action.
- The agent keeps a per-relay journal (`git/relay/<id>/tips.json`) rather than a single journal file.
- `hosting` in the heartbeat is `{ able, reason, free }`; the per-machine reason shown on the card is the
  agent's own text or "This machine's agent cannot keep copies yet (update it)" for agents without the label.
- Tasks (`git_tasks`) are handed out on `git/poll` after relays, one per machine at a time, and run on the
  agent's task thread beside relays (`HostedGitTasks`); blob transfers use `git/task/:id/{body,part,complete}`.
- Recovery order (§6) is simpler than planned: a current copy is promoted; otherwise a restore runs (automatically
  for a lost repository, or after a day offline with no current copy, or on request). A stale copy that is online
  is not promoted "by the delta"; it syncs once a primary exists and keeps aside what it had beyond the record.
- Promote of a recovered ref is a push by the holding machine through the relay with a write ticket for that one
  ref (the hook keeps the default branch fast-forward only), not a coordinator-side record change.
- Backups skip repositories over 1 GiB and degraded ones; SHA-256 is recorded for bundles up to 256 MiB, the size
  check applies to all. Project delete, the 30-day backup retention after delete and the out-of-band change flag
  remain for later.
